QASR: QUICK ATOMIC STRUCTURE RENDERER · V0.4.0 RELEASE

Download worker-requests.jsonl and CONTCAR.co into one directory. Run qasr --batch < worker-requests.jsonl there. It writes worker-top.png and worker-oblique.png and returns three responses, including cache statistics. Worker schema.

M10 — Sequential JSONL worker

Available in v0.4.0. --build-info reports batch_worker: true. The original single-job CLI remains supported and shares its rendering path with the worker. No additional runtime package, network listener or HTTP service is required. MCP remains an optional integration adapter when a client needs it; this implementation delivers the persistent rendering/batch branch of M10.

Start and call

qasr --batch --cache-mib 64 < requests.jsonl > responses.jsonl
qasr --schema worker > worker.schema.json

--batch must be the first argument. Its only options are --cache-mib 0..512 (default 64, zero disables retention) and --max-jobs 1..1000000 (optional; otherwise process until EOF). Options cannot be repeated. Every nonblank input line is one strict JSON object, at most 1 MiB excluding its terminating newline. A final valid line without newline is accepted. Blank lines are ignored. Oversized/NUL/malformed lines produce an error response and are drained through the next newline so later requests can continue. JSON nesting is limited to 32 including the envelope. Duplicate/unknown keys remain errors.

{"id":"view-1","op":"render","job":{"input":"CONTCAR","output":"view-1.png","threads":4,"config":{"image":{"width":768,"height":768},"camera":{"view":"top"}}}}
{"id":"view-2","op":"render","job":{"input":"CONTCAR","output":"view-2.png","threads":4,"config":{"image":{"width":768,"height":768},"camera":{"view":[1,1,1]}}}}
{"id":"check","op":"validate","job":{"input":"CONTCAR","config":{"geometry":{"expand_xy":[1,1]}}}}
{"id":"memory","op":"stats"}
{"id":"release","op":"clear_cache"}

IDs are required printable ASCII strings of 1..128 bytes. Operations are render, validate, stats and clear_cache. Render/validate require an ordinary M9 invocation under job; control operations reject a job field. All paths are relative to the worker's working directory, equivalent to stdin JSON jobs. No shell commands or input-data uploads are accepted. Create output parent directories before submission. Input structures remain files; PNG stdout remains unsupported. Worker jobs always skip implicit user preferences, even if their no_user_config field is false; put reproducible settings in each request.

Exactly one response is flushed per nonblank line; stdout contains only JSONL. Successful renders return the normal compact report under result, with cache and actual render-thread information. Malformed/unusable IDs are null when they cannot be echoed; clients should check ok rather than assuming an ID implies success. IDs need to distinguish outstanding work; the worker does not retain an ever-growing history of IDs.

{"id":"view-1","ok":true,"result":{"ok":true,"version":"0.4.0","input":{"path":"CONTCAR","sha256":"…"},"output":{"path":"view-1.png","sha256":"…"},"cache":{"source_hit":false,"scene_hit":false,"retained_bytes":12345,"limit_bytes":67108864},"render_threads":4}}
{"id":"bad-selection","ok":false,"error":{"code":"invalid_atom_index","exit_code":2,"path":"atom_overrides[0].select.source_indices[0]","message":"…"}}

The success example is abbreviated; actual reports also include dimensions, counts, settings, timings and cumulative cache counters. job.report optionally writes the result to a separate file; omitted or "-" sends no extra stdout message. PNG and report file commits are individually atomic, not a combined transaction. A late sidecar-report I/O failure can leave a valid new PNG. Diagnostics/recovery warnings use stderr. Config/rules/paths are rebuilt per job; ordinary request errors preserve the session and later requests continue.

validate returns input_validated and selectors_validated. With no input, these are false and only settings syntax/resolution is checked. Validation evicts retained input/scene data before parsing, so it shares the normal memory budget. It never writes PNGs or render reports.

Cache policy and limits

The worker retains at most one parsed structure and one matching scene. There is no unbounded filename map, trajectory history, image cache or queue. The default limit is 64 MiB of retained atom/scene/style-metadata allocations. An object too large for the limit still renders under existing per-job budgets, without being retained. stats reports the limit, retained bytes, lifetime source/scene hit counters and source misses. clear_cache drops objects, while keeping lifetime counters. Per-job parser/scene/image/work limits still apply; the cache limit does not represent the worker's total RSS or a global pool limit.

  • Input reuse requires matching content SHA-256, explicit format, frame/final selection, recovery policy and ordered species mapping. Each request rehashes the input; timestamp/inode/size alone are insufficient. A miss is hashed again after parsing to detect ordinary concurrent modifications during that pass.
  • Changing input identity/options evicts the prior entry. Failed parsing does not install a partial result. Input content reuse can work across different paths; reports still name the current request's path.
  • Scene reuse additionally requires matching resolved geometry, element styles, bond cutoffs, atom rules and cell visibility. Camera, image dimensions, AA, lighting style, PNG settings and annotation layout are recomputed per request.
  • Geometry/rule changes rebuild the scene. A different frame currently requires another full validated parse; only the selected structure is cached. Alternating frames can therefore miss even when the file is unchanged.

Inputs must remain stable while an individual request is running. Hashing twice does not provide file locking or protect against arbitrary change-and-restore races. Cached structures/scenes own their allocations and do not borrow the prior request's configuration strings. All retention is released at normal shutdown.

Cancellation and lifecycle

The stream is sequential: finish a request before expecting a later control request to run. Clients can stop queuing by closing stdin; accepted lines are processed until EOF or the configured job count.

On POSIX/WSL, SIGINT during an active render/validation requests cooperative cancellation. The request returns error code cancelled (numeric category 8), and the worker can accept another request. Polling occurs during text/XML input, hashing, scene work and raster tiles; encoding/allocation/library calls may finish before the next check. A cancelled PNG is discarded if cancellation is observed before its atomic commit. Cancellation arriving after output commit cannot undo that output. Client hard deadlines may terminate the process instead.

SIGTERM requests cancellation and shutdown after the current response. An idle interrupt exits with status 130. Normal EOF/job-limit shutdown returns 0; request failures alone do not make the session exit nonzero. Fatal framing I/O/output failures return 7, allocation failures can return 6, and invalid launch arguments return 2. A client must inspect every response, independently of final exit status.

Benchmark and verify

Generate the synthetic corpus, then compare both backends using the same executable, corpus, filesystem and thread policy:

python3 tools/run_m10_workloads.py build-release/qasr /tmp/m10-data \
  --output /tmp/m10-cli --samples 30 --warmups 3
python3 tools/run_m10_workloads.py build-release/qasr /tmp/m10-data \
  --backend worker --cache-mib 64 --output /tmp/m10-worker \
  --samples 30 --warmups 3 --reference /tmp/m10-cli/report.json

The worker runner checks IDs, errors, input/output hashes, frames, counts, decoded pixels and restoration assertions against the CLI. Warmups exclude startup and initial cache misses from repeated-request latency; raw stages and cache hits remain in the report. Worker per-request CPU samples are null because child resource accounting is only available when a child exits. With --measure-rss, the worker's whole-session peak is measured once with GNU time, whereas CLI peaks are separate per-request runs. Do not compare those as identical memory metrics.

Eight worker test groups cover framing/errors, scene-key dependencies, disabled and small caches, clear/validate, synthetic CLI equivalence, bounded repeated use, launch/schema/default isolation and active cancellation/recovery. The broad release/sanitizer/fallback checks and measured results are documented with M11.

M10/M11 implementation and validation — 2026-10-29

M10 delivers a sequential JSONL worker with a shared CLI rendering path, content-sensitive bounded input/scene reuse, strict request schemas, structured responses, cache controls and cooperative cancellation. See batch-worker.md and synthetic-workloads.md. MCP/HTTP remain optional integration layers; no service dependency was added.

M11 investigated OpenMP opportunities using both synthetic and retained real structures. It retains parallel buffer initialization, primitive projection and premultiplied-AA resolution when enough work is available. Each iteration owns its output, so no floating-point reduction or shared primitive append is needed. Raster tiles retain deterministic primitive ordering and dynamic scheduling. Raster cancellation is checked once per tile with a lock-free atomic flag. The normal CLI and persistent worker both benefit.

Threading decisions

  • Initialize sample buffers in parallel for at least 1,048,576 samples.
  • Project primitives in parallel for at least 4096 primitives.
  • Resolve antialiasing in parallel for at least 262,144 output pixels.
  • Keep the existing auto policy: one thread below 512² pixels, otherwise up to eight, respecting runtime availability. Explicit thread settings still work.
  • Preserve the OpenMP-disabled path and ordinary output. Reports now include actual render_threads, in addition to requested thread settings.

Parsing and SHA-256 hashing remain sequential. The input parser is a streaming state machine, while standard SHA-256 has chained state; adding naive OpenMP loops would not preserve their semantics. Selector rules have later-rule precedence, scene/bond construction has ordered append and shared work/allocation budgets, and PNG encoding uses stateful library APIs. These were reviewed but not parallelized in this iteration. More involved redesigns need their own measurements; the repeated-input cache already avoids much scene work.

Static and guided tile scheduling were tested in prototype builds. Static was substantially slower on the AA-heavy workload; guided gave mixed results across cases/thread counts. Neither replaced the existing dynamic policy. Prototype source and binaries, compile flags, executable hashes and raw results are retained under artifacts/m11/ and the native temporary build directories.

The standard native-WSL comparison uses the same corpus, binary, filesystem and one render thread in both backends: five measured repeats per request after two warmups. All 53 requests pass independent correctness/reference checks. The stress comparison uses nine frame/invalidation requests from the 4096-atom, 512-frame corpus (109.5 MB XML), five repeats after one warmup.

Ratios summarize successful request medians; expected failures are excluded. These are warm repeated-request results. Per-recipe warmups populate caches, so initial parsing, new-style scene rebuilds and first-miss double hashing are not represented in those medians. They do not promise the same gain for a single pass over distinct files/styles. The single-slot cache can miss when alternating frames. Whole-worker GNU-time peak RSS was 25,240 KiB for standard and 42,620 KiB for stress. This includes transient rendering/encoding and allocator/runtime memory, not just retained cache bytes. CLI memory measurements are separate per-request runs and are not the same metric. Raw samples, hashes and cache metadata are in artifacts/m10/native-*/report.json. The measurements predate small defensive allocation-failure checks; final correctness checks cover the delivered source.

M11 latency and CPU evidence

Intel i9-10900K, 20 logical CPUs, WSL; native temporary output, fixed libpng level 1, warm cache. Four workloads were swept at 1/2/4/8/16 threads with eight samples and two warmups for the baseline, retained setup changes, static and guided scheduling. Every measured PNG had to equal the corresponding reference bytes. A separate confirmation used 30 samples after three warmups at eight threads.

Small 128² jobs were also checked. Their process/thread startup variability is large relative to the useful work, so their results do not justify raising the automatic small-job thread count. The retained changes target sufficiently large loops. These are combined-change measurements, not isolated attribution to each new region. Lower latency does not imply lower CPU cost: annotations used more CPU in the confirmation. Raw median/p95/min/max, wall/CPU samples and stage times are in artifacts/m11/sweep.json and confirmation.json. The runs are sequential rather than randomized, and OS cache/host scheduling are uncontrolled; no universal speedup or formal confidence-interval claim is made.

Worker/thread combinations

A separate native-WSL experiment rendered identical 1000-atom, 1024², 2× AA jobs through warm persistent workers. It tested 1/2/4 workers × 1/2/4/8 render threads, 12 jobs per sample, three samples after warming every worker.

Configuration Median jobs/s Idle sum of worker RSS, KiB
1 worker × 8 threads 11.76 27656
4 workers × 4 threads 25.58 110520
4 workers × 8 threads 22.37 110652

Four workers × four threads improved throughput for this workload at a higher aggregate memory footprint. Raising the per-worker count to eight lowered throughput. RSS values are idle snapshots, not aggregate peak measurements. The raw pool report includes CPU time from /proc ticks and exact PNG hashes. These results motivate explicit per-job thread counts when using a pool; they do not justify imposing one global policy on all machines or workloads.

Correctness, resources and deployment

The synthetic baseline covers independent structures, repeated views/styles, frame changes/errors, periodic contexts, state restoration and same-identity content replacement. Cache retention is bounded even over repeated requests; small/disabled caches, clear/validate operations and malformed/oversized input are tested. Cancellation tests preserve an existing destination, receive a cancelled response and successfully reuse the worker. Large transparent/adaptive renders compare one/eight-thread PNGs to cover the newly parallel regions.

A separate 1200-request, changing-style/context soak held cache retention below 1 MiB. After the first 200 requests, idle RSS samples spanned only 8 KiB on this run; this is an observed plateau, not a universal RSS bound.

All 12 Release, 14 all-feature address/undefined-behavior/leak and 12 reduced-dependency CTest entries passed. All 20 retained default reference images remain pixel-identical. Installation, binary/source packaging, fresh offline source rebuild/tests and fallback deployment checks passed. These checks are retained under artifacts/m10/validation/ and artifacts/m10/deployment/. No runtime dependencies beyond the existing build were added. Synthetic data and performance timing evidence are generated local artifacts; source, tests, schemas and documentation are versioned. WSL is the user-approved environment.

Synthetic data for M10 and M11

tools/generate_m10_workloads.py creates original, seeded POSCAR and minimal vasprun.xml inputs, geometry oracles and request plans using only the Python standard library. No external dataset, scientific Python package or VASP license is needed. These are artificial rendering/parser workloads, not physically validated structures or results of a DFT/MD calculation. They complement the retained real fixtures; they do not establish real-world performance by themselves.

Generate and use

Run from the repository root with the M9-capable executable on master:

python3 tools/generate_m10_workloads.py \
  --profile standard --seed 1729 --output artifacts/m10/data

# Check file hashes, species/order, cells, frame counts and Cartesian positions.
python3 tools/run_m10_workloads.py build-release/qasr \
  artifacts/m10/data --validate-only

# Establish a baseline using independent CLI calls, before implementing a worker.
python3 tools/run_m10_workloads.py build-release/qasr \
  artifacts/m10/data --output artifacts/m10/baseline \
  --samples 30 --warmups 3 --measure-rss

Both tools refuse existing output directories. Choose a new path for each dataset or measurement; there is no force/overwrite option. Data generation and oracle verification occur outside the timing interval. Treat measurements as warm-cache runs: neither script flushes OS caches. Use a quiet machine and record storage placement; native WSL storage and /mnt/d can have different I/O costs.

The generated data is reproducible for the same generator version/source, seed and parameters. The manifest has no timestamps or absolute paths. SHA-256 file hashes and a generator-source hash identify the exact corpus. The generator uses an integer hash for jitter and an integer triangular motion pattern, avoiding a random-library or trigonometric dependency. The XML writer streams frames and retains only one geometry/frame in memory.

Sizes use decimal units. Counts include negative cases; XML-specific requests are skipped explicitly for XML-disabled builds. Fourteen, 22 and 34 input files are generated respectively, including paired POSCAR frame snapshots and one intentionally malformed POSCAR. XML contains an initial structure plus the stated number of calculation frames; there is no extra finalpos geometry.

Override --atoms, --frames, --structures, --variants and --image-size to isolate scaling effects. Atom counts are 4..10000, frames 2..4096, structures/variants 2..128, dimensions 64..2048, seed 0..2^32−1. A conservative 512 MiB estimate rejects oversized combinations before creating the dataset. Renderer geometry/work limits still apply: a permitted generated input can be expensive or exceed rendering budgets under aggressive settings. Large profiles are deliberately optional; the CTest entry uses smoke data.

Contents and intended experiments

  • inputs/POSCAR.bulk: alternating toy Si/O lattice with small deterministic jitter. The spacing exercises ordinary bond construction.
  • inputs/POSCAR.skew: a sheared Si/O cell with the same source-order discipline.
  • inputs/POSCAR.slab: a Co slab with xy periodicity and explicit z vacuum.
  • inputs/POSCAR.boundary: two H atoms outside opposite primary-cell faces, exercising wrapping and short periodic bonds. Source Cartesian x coordinates are −0.1 and 4.1 Å in a 4 Å cell.
  • inputs/vasprun.synthetic.xml: a complete geometry-only trajectory with known, deterministic bounded displacements, correct atom/type metadata and stable source indices. It is suitable for this renderer, not a full VASP output emulator.
  • oracles/: full element/order, lattice and Cartesian positions for static inputs and first/middle/final trajectory frames. Matching POSCAR snapshots allow cross-format pixel checks. The runner checks parser results against these values with an absolute 1e−9 Å tolerance before measuring.
  • manifest.json: parameters, provenance, file sizes/hashes and plan inventory.

The seven workload families are:

Family What it exercises
independent Different structures, sizes, species and cells; process scheduling
views Repeated views of one input; parsed-input/scene reuse opportunities
styles Repeated styles, backgrounds, radii and source-atom colors; cache-key correctness
frames First/middle/final frames, returning to frame 0, an invalid frame, then recovery
periodic Centered copies, muted/greyscale colors and periodic boundary geometry
isolation A baseline, changed dimensions/style/repeat/cell settings, malformed input, invalid selector, then the original baseline
invalidation Original → changed → restored geometry at one private input path, retaining its inode, byte count and mtime

For invalidation, only the runner-owned copy is overwritten. The source corpus is immutable. Replacement changes the cell and coordinates while preserving text length; the runner verifies that its pixels change and then return exactly to the original pixels. The report records size, inode and nanosecond mtime so that a future cache cannot accidentally pass by relying only on those identity fields. This deliberately tests content-sensitive invalidation; it does not claim to solve arbitrary concurrent input modification.

Request plans and the baseline runner

plans/*.jsonl contain driver envelopes, not a currently supported renderer batch protocol. Each line has id, action, requires, an ordinary M9 job and expected assertions. Paths are relative to the suite root. The runner resolves paths and submits each job using the existing qasr --job - interface. The optional active_input field requests the private input-replacement scenario. A future M10 worker adapter can reuse these envelopes and expected outcomes.

The runner supports --backend cli (default, independent processes) and --backend worker (one persistent M10 session). Use --reference to compare worker results with the CLI, and --cache-mib 0 to isolate persistence from caching. The worker tests additionally check bounded retention, cancellation and state restoration. See the worker interface. Hard-coded expected pixel hashes are avoided because compiler/library/host changes may affect them; a retained run supplies exact comparison hashes in a controlled environment.

Each measured request checks:

  • Expected exit status and structured errors. Intentional failures must preserve a sentinel output file, and subsequent requests must succeed.
  • Input/output SHA-256, selected frame, atom count and image dimensions.
  • Repeatable decoded RGBA, plus restoration/difference assertions in the plans.
  • With --reference, matching request/input/error/count/pixel results before reporting latency ratios. A failed or different-corpus reference is rejected.

For a selected experiment and optional thread comparison:

python3 tools/run_m10_workloads.py build-release/qasr \
  artifacts/m10/data --families views styles \
  --output artifacts/m10/one-thread --samples 30 --warmups 3 --threads 1

python3 tools/run_m10_workloads.py build-release/qasr \
  artifacts/m10/data --families views styles \
  --output artifacts/m10/auto-threads --samples 30 --warmups 3 --threads auto \
  --reference artifacts/m10/one-thread/report.json

Defaults are three measured samples and one warmup per request, with one render thread from each generated job. --threads overrides that setting. Reports checkpoint after every request and become passed: true only when the complete selected plan succeeds. Timing includes process startup, input hashing, rendering, PNG output and success-report generation; oracle checks and PNG decoding are outside the timed region. Median/p95 and raw wall/CPU/stage samples are retained. CPU accounting assumes sequential children without unrelated concurrent child processes. --measure-rss uses one separate GNU /usr/bin/time invocation per request, reporting peak RSS in KiB; it is not a steady-state worker-memory measure. There are no speedup confidence or cold-cache claims.

Verification and next stages

Seven automated tests cover reproducibility/seed changes, destination and size bounds, geometry oracles, independent XML/POSCAR parsing, corpus tampering/path confinement, all workload families, unchanged failure outputs, same-identity replacement and reference-comparison rejection. The same suite is exercised with Release, sanitizer and XML/OpenMP/libdeflate-disabled renderer builds.

M10 implements the persistent worker and reference comparisons. M11 is recorded in the detailed design: profile candidates for OpenMP, sweep thread counts/scheduling and worker/thread combinations, and retain improvements only when measurements justify them.
